# 2026-11-01 音频编码修复

适用版本：0.1.1。来源为本次 OBS WebSocket 实查、OBS 日志、MediaMTX 运行日志和本机 Chromium 音频采样。

## 现场状态与根因

用户已在 OBS 将视频调整为 1920×1080、60fps、10000 kbps。10:45:06 的 OBS 日志显示实际启用 `FFmpeg aac encoder: adv_stream_audio`，LAN Stream 的 `AdvOut.AudioEncoder` 为 `ffmpeg_aac`；MediaMTX 同时报告 Opus 轨道。

这两个记录存在实质冲突：OBS 的 WHIP 输出将音频声明为 Opus，并按 Opus RTP 方式发送编码器提供的数据，不负责把 AAC 转成 Opus。因此服务器显示 Opus、连接建立成功和音轨存在，均不能证明音频数据有效。配置不匹配会造成接收端音频解码异常，是本次已确认的错误；未在用户远端播放设备上直接记录修复前后的听感。

实现依据：[OBS WHIP 输出](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-webrtc/whip-output.cpp)，重点为 Data、ConfigureAudioTrack 和 register_whip_output。

现场桌面音频与麦克风均静音，测试视频已被用户隐藏。它们的增益、同步偏移、监听、静音与节目场景均保留。修复不会把静音当作错误解码的解决办法，也不会自动打开话筒。

## 修复

1. 在 `dev/artifacts/audio-repair-20261101-105033` 保存本次 LAN Stream 配置、场景和运行快照的备份。
2. 停止本项目推流，将高级输出音频编码恢复为 `ffmpeg_opus`，重新加载当前配置并恢复直播。
3. 确认日志为 FFmpeg libopus encoder，128 kbps、48 kHz、双声道；视频仍为 1080p60、10000 kbps。
4. 启动器对当前输出模式的音频编码进行检查：高级输出为 FFmpeg Opus，简单输出为 Opus。不匹配时提示 OBS 中的设置位置，失败细节由既有诊断机制保存。不自动改写用户参数，也不因检查失败停止用户已有直播。

## 验证

- 修复后静音基线：浏览器 Web Audio PCM 的 RMS 与 peak 均为 0；音频 RTP packetsLost 为 0。
- 临时启用已存在的低音量测试视频，浏览器静音、分析节点不连接扬声器，避免本机回放反馈。采样得到 dominantHz **439.453125**，RMS **0.007042967528731517**，peak **0.010223700664937496**，与已知 440 Hz 测试源一致；packetsLost 为 0。测试后恢复原场景项目的隐藏状态，未保存节目音频。
- 编码检查回归：仅临时改变配置参数为 AAC，保留当时正在运行的 Opus 编码器，Start 返回失败并明确提示 requires Opus；没有开始 AAC 推流，没有中断已有直播。随后恢复配置参数为 Opus，Start 正常复用原进程。
- 修复结束时直播保持运行，浏览器诊断会话主动关闭；保留用户原先运行的 OBS 和 MediaMTX，不新增后台服务。

## 使用要求

需要直播电脑声音时，在 OBS 混音器解除“桌面音频”的静音；麦克风按实际需要开启。本机观看页保持静音，避免收到的节目声音再次进入桌面采集。观看设备刷新播放器后重新播放并解除播放器静音。
